# Question 2 — AI question generation with duplicate prevention and independent detection

Two layers that share no model and no code path:

1. **Prevention, during generation.** The generator shows the LLM a compressed, budgeted map of what the bank already covers and steers it toward uncovered concepts. It rejects too-close candidates in the loop and feeds them back to the next round.
2. **Detection, after generation.** An independent detector checks every new question against the whole collection. It flags exact duplicates, paraphrases and effectively-equivalent questions, and sends genuinely ambiguous pairs to review.

Full run with every required example: **[examples/REPORT.md](examples/REPORT.md)** (regenerated by `scripts/run_demo.py`).

| | Result |
|---|---|
| Assignment corpus Q1–Q10 (held out) | **10/10** correct, offline and with the LLM judge |
| 52 labelled calibration pairs, offline | 88 % accuracy, **100 % duplicate precision**, 0 duplicates passed as unique |
| same, with LLM judge for the grey zone | **98 %** accuracy, 100 % duplicate precision, 95 % recall |
| Generating 8 new “reflection of light” questions over a 145-question bank | this workflow **0/8 duplicates** (1 sent to review) vs naive prompt 1/8 duplicates + 4 for review |

## Architecture

```
                   ┌──────────── prevention (qgen/generator.py) ────────────┐
 topic, n, scope ─►│ retrieve relevant (MiniLM) → cluster into concepts      │
                   │ → budgeted prompt → LLM → novelty filter (MiniLM)       │──► candidates
                   │        ▲ rejected candidates fed back ─┘                │
                   └─────────────────────────────────────────────────────────┘
                   ┌──────────── detection (qgen/detector.py) ──────────────┐
 candidate ───────►│ exact key → top-k retrieval (bge-small, whole bank)     │──► exact / semantic /
                   │ → signal cascade (+ cross-encoder) → LLM judge if grey  │    needs_review / unique
                   └─────────────────────────────────────────────────────────┘
 qgen/pipeline.py: duplicates dropped, needs_review stored with status + duplicate_of, unique stored
 qgen/store.py:    SQLite questions + (question_id, key, value) tags + cached embeddings
```

## 1. Duplicate avoidance during generation

**Choosing which existing questions to show, without exceeding context limits** (`QuestionGenerator.select_context`):

1. **Retrieve.** Embed the topic and take the most relevant questions (cosine ≥ 0.35, at most 400). An optional tag filter scopes the pool, e.g. `chapter=light`.
2. **Compress into concepts.** Agglomerative clustering (average linkage, cosine ≥ 0.80) collapses paraphrase families into one concept. "What is / Define / What do you understand by / Explain the meaning of reflection of light" become a single line with a variant count. "State the laws of reflection" stays separate.
3. **Budget.** Emit one representative per concept, most relevant first. Lines are truncated to 140 characters, and a rewording example is shown for the first three families so the model sees what "same question" means. Emission stops at a token budget (default 1500) with an "… and N more concepts" line. In the demo, 145 questions → 103 relevant → 75 concepts → 48 shown in ≈1.5k tokens.

**Steering away from paraphrases.** The system prompt states that rewording does not make a question new and lists the classic rewordings. It also lists what does count as new: a different sub-concept, law, reason, comparison, numerical with new values, application, diagram reasoning, misconception check or experiment. The model first names the uncovered concepts it will target, then writes one question per concept.

**In-loop novelty filter.** Each candidate is embedded and compared with the relevant pool and with questions accepted earlier in the run. Exact-key matches and candidates with cosine ≥ 0.82 are rejected. Rejected candidates and their nearest neighbours go into the next round's prompt ("rejected because they duplicated…"), and the loop runs up to 3 rounds until `n` questions are accepted.

**Scaling as the collection grows:**

* Prompt size is bounded by the token budget and grows with the number of distinct concepts that fit, not with the number of stored questions.
* Clustering runs only on the retrieved pool (≤ 400), so it costs the same for 1k or 1M questions.
* Embeddings are computed once and cached in SQLite per model. Retrieval is exact cosine search, measured on this laptop at 0.13 ms/query for 1k questions, 0.95 ms for 10k and 8.9 ms for 100k. Beyond ~1M an ANN index (HNSW via hnswlib or FAISS) slots in behind `VectorIndex.search`.
* Tag scoping (`--scope chapter=light`) shrinks the pool further for huge banks.

## 2. Independent duplicate detection

`DuplicateDetector.check(text)` runs on every candidate against the **entire** collection. It never filters by tags, and it uses a different embedding model (bge-small vs the generator's MiniLM) plus signals the generator doesn't use. The demo shows why this matters: a generated question with mirror-reversed letters ("ƎƆИAJUBMA") scored only 0.37 in the generator's filter, but the detector matched it to the bank's AMBULANCE question.

**Layers:**

1. **Exact.** A formatting-insensitive key (NFKC, case, punctuation, whitespace, articles, `°` → "degrees", `1,000` → `1000`) is an O(1) lookup. A character-similarity ratio ≥ 97 with identical numbers catches typos.
2. **Retrieval.** Top-8 neighbours by bge-small cosine.
3. **Pair cascade.** Every signal is stored as evidence in the verdict.

| Step | Rule | Example |
|---|---|---|
| numeric givens | different numbers, or numbers vs none → **unique** | "angle of incidence is 30°…" vs "…55°…", Q7 vs Q6 |
| answer intent | both specific and different (definition / law / difference / calculation / example / application) → **unique** | Q5 *laws* vs Q1 *definition*; Q9 *difference* |
| same concepts | identical content-term sets (cue words like define/explain/meaning/understand removed, light stemming) + compatible intent + cos ≥ 0.80 → **semantic duplicate** | Q2, Q3, Q4 vs Q1 |
| paraphrase model | cross-encoder (`quora-distilroberta-base`) ≥ 0.90 and cos ≥ 0.90 → **semantic duplicate** | "SI unit of force" / "Name the SI unit of force" |
| scope | one question's terms are a strict subset of the other's (≤ 2 extra) and cos ≥ 0.75 → **needs review** | Q8 "What is reflection?" vs Q1 |
| compound | a self-contained sub-question is an exact or semantic duplicate → **needs review** (partial overlap) | "State the two laws of reflection. Draw a ray diagram…" |
| grey zone | cos ≥ 0.90 or cross-encoder ≥ 0.50 → LLM judge, or review when offline | "concave mirror" vs "convex mirror" |
| otherwise | **unique** | |

4. **LLM judge** (`claude-haiku-5.5`, temperature 0) decides grey-zone pairs as duplicate, different or ambiguous, with a reason. For *scope* pairs it may rule them different or ambiguous but **cannot auto-merge** them. Whether "What is reflection?" equals "What is reflection of light?" depends on context the judge doesn't see, which is exactly the assignment's "review context" case.

A candidate's verdict is its most severe pair verdict: exact > semantic > needs_review > unique.

**Design principle: fail safe.** Neither offline nor with the judge does the detector merge two different questions (100 % duplicate precision on calibration) or silently pass a known duplicate or review case as unique. All its errors fall into `needs_review`.

## 3. Tags

`question_tags(question_id, key, value)` takes any new key or value at any time, multiple values per key included. `store.all(tags={...})` filters by them, and the generator can scope its context with them. **Neither layer compares tags.** `check()` accepts text only, so a copy with different tags is still a duplicate, and two different questions with identical tags are not (`tests/test_detector.py::test_detection_ignores_tags`). Generated questions are stored with `source=llm`, the caller's tags and a `concept` tag.

## 4. How accuracy and performance are evaluated

* **Held-out test set.** The assignment corpus Q1–Q10, inserted in order, each classified against its predecessors; the matched question is checked too.
* **Calibration set** (`data/calibration_pairs.json`): 52 labelled pairs on *other* topics (refraction, photosynthesis, motion, electricity, acids, cells, mirrors), covering formatting duplicates, paraphrases, scope cases and hard negatives (first vs second law, force vs work, concave vs convex, same template with new numbers). All thresholds were set on this set, never on the test corpus.
* **Metrics:**
  * 4-class confusion matrix and accuracy;
  * duplicate precision, the cost of wrongly deleting a good question;
  * duplicate recall, the cost of a duplicate slipping in;
  * "passed as unique" count, the silent failures;
  * review-queue rate, the human cost;
  * ms per check.
* **Generation metrics:**
  * duplicate rate of a generated batch as judged by the independent detector, compared with a naive no-context prompt (ablation in the report);
  * rejection rate and rounds in the loop;
  * max-similarity distribution of accepted questions;
  * prompt tokens per request.
* **Scale:** retrieval latency at 1k, 10k and 100k vectors (`evaluate.scale_benchmark`).
* **In production:**
  * grow the labelled set from review-queue decisions, since every human verdict is a free label;
  * re-calibrate thresholds periodically;
  * track the judge's agreement with reviewers;
  * sample accepted-as-unique questions for audit to estimate the silent-miss rate.

## Technology choices and trade-offs

| Choice | Why | Trade-off |
|---|---|---|
| Two different bi-encoders (MiniLM for generation, bge-small for detection) | Independence: one model's blind spot isn't shared | Two models to host (both small, CPU-friendly) |
| Transparent signal cascade instead of one similarity threshold | Pure cosine can't separate "Define X" from "State the laws of X" (cos 0.84–0.90) or Q8 from Q1; the cascade explains every verdict | Hand-written cue-word list and intent patterns are English- and exam-style-specific |
| Off-the-shelf Quora cross-encoder only as one signal | Strong on question paraphrases, but scores "Define X." vs "What is X?" near 0 and concave vs convex at 0.98 | Fine-tuning on the review-queue labels would let it carry more weight |
| LLM judge only for the grey zone | Catches what rules can't (mitochondria "function" vs "role", concave vs convex); clear-cut pairs never reach it | Latency and cost on those calls (≈0.6 s); offline fallback is human review |
| Numeric variants count as different | "30°" and "55°" have different answers; banks want both | A bank that treats templates as duplicates can switch this rule off |
| Clustering + budget for context | Constant prompt size, paraphrase families shown once | Concepts beyond the budget aren't shown, so the in-loop filter and detector cover them |

## Data

* `data/corpus.json`: assignment Q1–Q10 with expected classes and deliberately inconsistent free-form tags.
* `data/bank.json`: 140 *Light*-chapter questions across 7 sub-topics, with paraphrase families, generated once by `scripts/build_bank.py` and committed.
* `data/calibration_pairs.json`: the 52 labelled pairs.

## Limitations

* Synonym-only paraphrases with no shared terms rely on the cross-encoder or judge.
* Content terms use a light stemmer, not lemmatisation.
* Compound-question splitting is sentence-based.
* The generator's quality depends on the LLM. The detector bounds the damage but can't create diversity.
