# Question 1 — Image catalog, object detection, metadata and composites

A working catalog service (Python library + CLI + REST API + browser UI) that

* stores images and their metadata,
* detects objects automatically in **photos and cartoons** (names, colours, confidence, boxes),
* lets users add / edit / delete objects, with **corrections kept as the source of truth** until detection is explicitly re-run,
* builds **composite images from existing catalog assets** from a natural-language instruction, and saves them as new catalog entries with full provenance.

The run of every required scenario is in **[examples/REPORT.md](examples/REPORT.md)** (annotated images, tables and composites, regenerated by `scripts/run_scenarios.py`).

## Quick start

```bash
# from the repository root
uv venv .venv --python 3.11          # or python -m venv .venv
uv pip install --python .venv/Scripts/python.exe -r question1/requirements.txt
cd question1

python scripts/make_test_images.py   # (re)draws the geometric test images; photos/cartoons are committed
python scripts/run_scenarios.py      # runs scenarios 1-7, writes examples/REPORT.md  (~4 min on CPU)
python -m pytest -q tests            # 29 tests, ~15 s (OWLv2 stubbed, no network)

python -m imgcat serve               # UI at http://127.0.0.1:8000 (catalog in runtime/catalog)
python -m imgcat add test_images/apple.png --name apple
python -m imgcat compose "Create an image containing one red apple and one orange" --verify
```

`OPENROUTER_API_KEY` (env or `.env` at the repo root) is optional. It is used only to turn instructions into composition plans; without it a rule-based planner is used. The first detection downloads OWLv2 (~600 MB) from Hugging Face. The detector runs on GPU if PyTorch sees CUDA and on CPU otherwise (~16 s per image on a laptop CPU).

## Architecture

```
            ┌────────────── imgcat ───────────────────────────────────────────────┐
 CLI ─┐     │ service.CatalogService   (single entry point, enforces the rules)   │
 API ─┼────►│   ├─ store.CatalogStore      SQLite: images / objects / detection_runs
 UI  ─┘     │   │                          + image files + object masks on disk    │
            │   ├─ detection.Detector     segmentation ⊕ OWLv2 fusion              │
            │   │    ├─ segmentation.py   background model, regions, colour layers │
            │   │    ├─ shapes.py         occlusion-aware circle/rect/triangle fit │
            │   │    ├─ owl.py            open-vocabulary detector (OWLv2)         │
            │   │    └─ colors.py         Lab colour naming                        │
            │   └─ composite             plan → resolve → cut out → layout → save  │
            │        ├─ planner.py        LLM planner (inventory-constrained) / rules
            │        └─ compose.py        resolver, cutouts, size priors, provenance
            └─────────────────────────────────────────────────────────────────────┘
```

### Data model: automatic vs user-editable fields

The split is enforced in the schema and the service, not just by convention.

| Level | Auto-generated, system-owned (read-only to users) | User-editable |
|---|---|---|
| Image | `file_name, sha256, width, height, format, kind (original/composite), style (photo/illustration), detection_status, detection_error, detector_version, detected_at, objects_source (auto/manual/composition), provenance` | `display_name, description, tags` |
| Object | `auto` JSON: `name, display_name, confidence, bbox, color, colors[{name,hex,fraction}], category, shape, attributes (occlusion, clothing colours, visible bbox…), detector, mask` | `user` JSON overrides: `name, display_name, color, confidence, bbox, category, attributes, notes, deleted` |

* Every object keeps the detector's output untouched in `auto`. User corrections are stored as overrides in `user`. What the rest of the system sees is `effective = auto ⊕ user`, so the UI can show "detector said X, you said Y" and revert one field at a time.
* User-created objects have `auto = NULL` and `origin = user`.
* Editing a non-editable field (e.g. `detector`) raises an error. Boxes must lie inside the image and confidence in [0, 1].
* `detection_runs` is an append-only history of runs. Each run records its output and, for a forced re-run, a snapshot of the objects it replaced, user edits included.

### Manual corrections are the source of truth

* Any add, edit or delete sets `objects_source = manual`.
* After that, `run_detection(image)` raises `ProtectedObjectsError` (HTTP 409; the UI asks for confirmation). Only `force=True` replaces the corrected objects, and the replaced set is archived in `detection_runs.replaced`.
* Deleting a detector object stores a tombstone (`user.deleted = true`), so a removed false positive stays removed and can be restored.
* Corrections persist across restarts; it's all SQLite. Scenario 4 in the report opens a fresh service on the same files.
* A failed run (`detection_status = failed`, e.g. a truncated file) never deletes existing objects.
* Composites get `objects_source = composition` and are protected the same way: their object list is exact, not a guess.

## Detection algorithm

The detector combines two complementary sources and records which one produced each field (`auto.detector`).

**1. Classical region proposals** (`segmentation.py`), used when the background is plain (≥ 85 % of border pixels share one colour):

* **Foreground.** Pixels further than ΔE 22 from the background colour in CIE Lab, minus soft shadows. Shadows are pixels darker than the backdrop but nearly as colourless.
* **Contact shadows** under photographed objects are trimmed. Only the bottom 20 % of a region is touched, and only low-chroma pixels are removed: measured fruit chroma is 50–77, shadow chroma 2–31.
* **Regions** are connected components, with parts closer than 9 px grouped, so a cartoon figure stays one object while separate shapes stay apart.
* **Colour-layer decomposition.** A region made of ≤ 5 flat colours, where each colour layer is a single blob that fits a geometric model, is split into one object per layer. That is how overlapping shapes separate. A cartoon boy is also flat-coloured, but its layers (outlines, skin on face and arms) are not shapes, so it stays whole.

**2. Occlusion-aware shape fitting** (`shapes.py`): circle (least-squares), rotated rectangle and minimum enclosing triangle are fitted **only to the region's true edge pixels**, the boundary pixels that touch background rather than another shape. A circle half-hidden behind a triangle still has a circular visible edge, so it is recognised, and the fitted model gives its **full (amodal) bounding box** plus `visible_fraction`. Layer *j* is recorded as hiding layer *i* when *j* covers the hidden part of *i*'s fitted model, which recovers the stacking order (`occluded_by`). Square vs rectangle is decided by aspect ratio. A row or column of ≥ 3 equal, unoccluded rectangles in different colours is labelled as **colour swatches**.

**3. Open-vocabulary detection** (`owl.py`): OWLv2 (`google/owlv2-base-patch16-ensemble`) is prompted with text queries ("an apple", "a boy", "a triangle", …). One model handles photographs and flat cartoons without per-style training. Its output goes through class-agnostic NMS.

**4. Fusion** (`pipeline.py`):

| Situation | Result |
|---|---|
| Segmentation region overlaps an OWLv2 box | OWLv2's **name** and score, segmentation's tight **box** and **mask**. If one blob holds two confident OWLv2 boxes (touching objects), it is split along those boxes. |
| Flat shape layer | Geometric label. Confidence is the fit score, raised when OWLv2 agrees: `1-(1-fit)(1-owl)`. |
| Region with no OWLv2 match | `unknown object`, confidence 0.2, `needs_review`. |
| OWLv2 box with no region | Kept if score ≥ 0.25 and the background isn't plain (cluttered photos), with a GrabCut mask. Dropped if it covers only plain background, a common false positive. |

**Colour** is a histogram of named colours (nearest Lab prototype per pixel) over the object's mask. The dominant chromatic colour wins. For people, `clothing_colors` is computed below the head, excluding skin, outlines and highlights; e.g. boy → blue, green, brown. **Style** (photo vs illustration) is the fraction of identical neighbouring pixels inside the foreground: flat art ≥ 0.65, photos ≈ 0.22.

**Statuses:** `detected`, `no_objects` (the run succeeded and found nothing: blank, noise), `failed` (the run broke: unreadable or truncated file), `composed`.

## Composite generation

1. **Plan.** An LLM converts the instruction into JSON items (`noun, count, color, is_category`) plus `layout` and `background`. It is given the **catalog inventory** and may only use those names; anything else must be listed as missing. If the LLM is unavailable or returns invalid JSON, a deterministic rule parser takes over. It handles counts ("one/two/3"), colour adjectives, plural categories ("colored shapes" → every distinct shape), layout words ("overlapping", "grid", "beside") and "on a blue background".
2. **Resolve.** Each item is matched to catalog objects by *effective* name, category and colour, so user corrections are respected. Candidates are ranked: unoccluded first, then images containing fewer objects (cleaner cut-outs), then user-verified, then confidence. A category request takes all distinct members from the single best image. **If anything is missing, `MissingAssetError` is raised and nothing is produced. The composer never generates a stand-in.**
3. **Cut out** each object from its *own source pixels*, using the stored detection mask. If the user has moved the box, the mask is recomputed: background subtraction inside the box, or GrabCut on busy backgrounds. A SHA-256 of each cut-out is stored.
4. **Scale and lay out.** Objects are scaled with real-world size priors (person ≈ 120, apple ≈ 8, graphic shapes a nominal 36) normalised so the tallest item is 420 px. Layouts:
   * `row`: bottom-aligned on a common ground line;
   * `grid`: category groups of three or more are packed into a 2-row block;
   * `overlap`: 30 % overlap, z-order in instruction order.

   Photographed items get a soft contact shadow.
5. **Save** as a new catalog entry: `kind = composite`, `objects_source = composition`. Placed objects carry exact boxes, z-index and their source object. The provenance records the instruction, plan, planner, every placement (source image, source box, mask method, scale, crop hash) and `generative_fill: false`. With `verify=True` the detector is re-run on the composite and must find every placed object; it does in all three demo composites.

## Technology choices and trade-offs

| Choice | Why | Trade-off |
|---|---|---|
| **OWLv2** open-vocabulary detector | One model for photos *and* cartoons; vocabulary is a text list, so new classes need no training | Slow on CPU (~16 s/image here; well under 1 s on a GPU). Boxes are looser than segmentation; it confuses square/rectangle and calls swatches "squares", which is why fusion keeps segmentation's geometry |
| Classical segmentation + geometric fitting | Pixel-exact boxes and masks on clean backgrounds, explainable, recovers occluded shapes and their order | Needs a plain background; on busy scenes the system falls back to OWLv2 + GrabCut |
| Hosted LLM only for *planning* | Free-form instructions → structured plan, constrained to the inventory | Optional. Rules cover the common phrasings offline. Pixels never come from a generative model, by requirement |
| No generative fill | The requirement says assets must not be silently replaced | Composites look like collages (cut-outs on a backdrop) rather than relit scenes; harmonising lighting would be a next step that still keeps source pixels |
| SQLite + files + JSON columns | Zero-ops, transactional, inspectable; `auto`/`user` JSON keeps field ownership explicit | Single-writer. A multi-user deployment would move to Postgres and object storage with the same schema |
| Size priors for scale | Sensible relative sizes from a few numbers | Priors are per-class constants; unusual instructions ("a giant apple") need an explicit size in the plan |

**Limitations I'd address next:** OWLv2 latency without a GPU (batching or a smaller model); colour naming is prototype-based, so very dark or desaturated objects can be called brown or grey; the shadow trim assumes a roughly horizontal ground plane; spatial relations beyond order and overlap ("on top of the table") aren't in the plan schema yet.

## Test data

`test_images/`: `shapes`, `colors`, `overlapping_shapes`, `blank`, `noise`, `camouflage` (a square ~6 grey levels brighter than its textured background, built to be missed) and `truncated` are drawn by `scripts/make_test_images.py`, with exact ground truth in `ground_truth.json`. `apple`, `orange`, `apple_orange`, `boy` and `girl` were generated once with an image model (`google/gemini-3.1-flash-image` via OpenRouter) and committed. The script draws simple procedural stand-ins if they are missing and no key is set.

## Results (from [examples/REPORT.md](examples/REPORT.md))

* Geometric images: every shape and swatch has the correct name and colour, with box IoU ≥ 0.986 against ground truth. The overlapping image yields three overlapping boxes with the correct occlusion order.
* Photos and cartoons: apple (red), orange, apple + orange as two separate objects, boy (clothing blue, green, brown) and girl (pink, …), all with tight shadow-free boxes.
* Failed detection: `camouflage` → `no_objects`, then the user adds the square. `truncated` → `failed`. `blank` and `noise` → `no_objects`.
* Corrections survive a non-forced re-run and a restart. A forced run replaces them and archives them.
* Composites: apple + orange; boy + girl + four shapes; an overlapping layer stack on a yellow background. A missing banana → `MissingAssetError`.
